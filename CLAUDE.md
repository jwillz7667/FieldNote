# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is right now

A built **monorepo**: `ios/` (SwiftUI + SwiftData client) and `server/` (NestJS API +
BullMQ worker), plus `docs/`, `openapi.json`, and CI. The full P0–P12 build is
complete — backend pipeline, iOS app, tests (43 server unit + 14 iOS XCTest), and
Railway deploy config all exist and pass locally. The original Xcode template scaffold
has been removed; `ios/` is the only iOS target.

**`FieldNote_Production_Handoff.md` is the source of truth.** It is the full product +
architecture spec and the de-facto README. Read it before doing any non-trivial work —
almost every design decision (stack, schema, API surface, build order, gotchas) is
settled there. This CLAUDE.md summarizes it; the handoff doc is authoritative when they
differ. Note one deliberate deviation: report compilation uses **DeepSeek**, not the
handoff's Claude Haiku — see `docs/adr/0002-deepseek-report-compiler.md`.

## The product

FieldNote turns a home inspector's spoken walkthrough into a branded PDF report. Core flow (the whole app): `+` → enter address → record while walking → stop → audio auto-uploads → **server-side** pipeline transcribes, compiles a structured report (sections → findings, each with a severity), and renders a PDF → user reviews/edits → shares PDF. Launch vertical is home inspection; the report is template-driven so it generalizes later.

## Architecture (full-stack)

The **monorepo** is `/ios` + `/server`. The four prime directives govern everything:

1. **"Simple" is a UI/UX rule only** — it constrains the iOS experience, not the backend. The server, data layer, storage, and AI engine are all production-complete, nothing deferred.
2. **Server is the source of truth.** Postgres holds canonical data; the iOS app is an offline-first SwiftData cache that syncs (last-write-wins by `updatedAt`).
3. **AI work is server-side.** The device only records and uploads audio. A BullMQ worker transcribes → compiles → renders.
4. **No secrets on the client, ever.** All provider keys live on the server; the app touches object storage only via short-lived presigned URLs.

Stack (locked decisions, see handoff §2/§17): iOS SwiftUI + SwiftData; **NestJS** API + worker on **Railway**; **Postgres** via **Prisma**; **BullMQ + Redis** queue; **Cloudflare R2** object storage; **Deepgram Nova-3** transcription; **DeepSeek** (`deepseek-chat`, OpenAI-compatible forced function-calling) for report compilation — swapped from the handoff's Claude Haiku 4.5 per `docs/adr/0002-deepseek-report-compiler.md`; **Puppeteer** HTML→PDF; **Sign in with Apple → app JWT** auth.

Pipeline (worker, idempotent + retriable, one `ProcessingEvent` per stage): download audio from R2 → transcribe → compile structured report → render PDF → upload PDF → `status = READY`. `JobStatus` walks `CREATED → UPLOADING → QUEUED → TRANSCRIBING → COMPILING → RENDERING → READY/FAILED`.

## Build, run, test (iOS)

The Xcode project is **generated by XcodeGen** from `ios/project.yml` (the `.xcodeproj`
is a build artifact and is gitignored) — run `xcodegen generate` after pulling or after
changing `project.yml`. The scheme is `FieldNote` (no space). The test target is
`FieldNoteTests` (14 unit tests covering APIClient/token refresh, sync/LWW, DTO
decoding — handoff §14). All commands run from `ios/`.

```bash
cd ios && xcodegen generate          # (re)generate FieldNote.xcodeproj

# Build for simulator
xcodebuild -scheme FieldNote -destination 'platform=iOS Simulator,name=iPhone 16 Pro' build

# Run tests
xcodebuild -scheme FieldNote -destination 'platform=iOS Simulator,name=iPhone 16 Pro' test

# Single test
xcodebuild -scheme FieldNote -destination 'platform=iOS Simulator,name=iPhone 16 Pro' \
  test -only-testing:'FieldNoteTests/APIClientTests/testRefreshesOnceOn401ThenRetriesSuccessfully'
```

Day-to-day, `xcodegen generate && open FieldNote.xcodeproj`, then ⌘R / ⌘U. Building
requires the **iOS 26 SDK (Xcode 26)** — the app targets iOS 26 and uses Liquid Glass
APIs. **Liquid Glass and accessibility must be verified on a physical iOS 26 device** —
the simulator under-renders glass (handoff §4.3).

Backend (`/server`, run from there): `npm run start:dev:api` / `start:dev:worker` for
watch-mode dev, `npm run build`, `npm run lint`, `npm test` (unit), `npm run test:e2e` /
`test:integration` (need Postgres+Redis+LocalStack via `docker compose up -d`),
`npm run prisma:migrate:dev`. The worker ships via `server/Dockerfile.worker`
(Puppeteer/Chromium); see `server/README.md` and `docs/DEPLOY-RAILWAY.md`.

## Non-negotiable constraints

- **Liquid Glass discipline (iOS, hard rule).** Glass belongs only to the *functional layer that floats above content* — record button, floating `+`, Export/Share control, system chrome (nav/toolbar/sheets adopt it automatically on the iOS 26 SDK). **Never** apply glass to the content layer (job rows, report/finding cards, transcript card, backgrounds) — glass-on-glass turns muddy. Must remain fully usable with **Reduce Transparency** on and full Dynamic Type; `accessibilityLabel` every icon-only control. Exact iOS 26 APIs and the mic↔stop morph are detailed in handoff §4.3.
- **Per-user scoping everywhere.** Every job query is scoped by `userId` from the JWT, enforced in the service layer (not just the controller). A user can never read or mutate another user's job. Never trust a client-supplied `userId`.
- **Idempotency on mutations.** `Idempotency-Key` on job create; stable job id on `/process` so retries never duplicate pipeline work. The worker re-running a `READY` job is a no-op.
- **Fail-fast config.** Backend refuses to boot if any required env var is missing/malformed (zod/Joi schema validation). See handoff §15 for the full `server/.env.example`.
- **Never fabricate findings.** The report compiler must only structure what's in the transcript; invent nothing, one severity per finding (`info|maintenance|repair|safety`), omit empty sections. Validate model output against the schema; retry once on malformed output, then fail the job cleanly.

## Build order

Work the phases in handoff §11 in order — **P0** repo/CI → **P1** API skeleton → **P2** auth → **P3** jobs domain → **P4** R2 media → **P5** queue/worker → **P6–P8** AI stages (transcribe / compile / PDF) → **P9** iOS core → **P10** iOS editing+sync → **P11** Liquid Glass + a11y → **P12** hardening. Each phase ends deployable with an acceptance gate; pause at each gate. v2 scope (real-time collab, team accounts, billing, second vertical, photos/live transcription) is explicitly out — flag, don't silently expand (handoff §3).

## Resolved config (was template drift — now settled)

The original template's mismatches with the handoff/standards are all resolved in
`ios/project.yml` — don't reintroduce them:

- **Swift 6 strict concurrency** is on (`SWIFT_STRICT_CONCURRENCY: complete`): the recorder/uploader are actor-isolated and UI + the SwiftData context are `@MainActor` (handoff §13).
- Bundle id is **`com.viralventures.fieldnote`** (handoff §15/§17) — the template's `Res.Field-Note` placeholder is gone.
- **No CloudKit.** Sync is the custom NestJS/Postgres backend (last-write-wins by `updatedAt`); the template's CloudKit/remote-notification entitlements were dropped.
- The template's throwaway `Item`/`ContentView` are replaced by the real domain models — `Job / ReportSection / Finding / Severity / JobStatus` plus local `syncState`/`pendingUpload` (handoff §4.2, §6).
